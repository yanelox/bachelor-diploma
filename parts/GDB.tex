\section{Отладчик GDB}
\label{sec:gdb} \index{gdb}

\subsection {Основная информация и возможности}
\label{gdb:general}

GDB (GNU Project Debugger) — это инструмент для поиска ошибок в программах,
предоставляющий средства анализа и управления их выполнением. Он поддерживает
множество языков программирования и позволяет запускать приложения под своим
контролем для пошагового изучения их поведения.

Одна из основных возможностей отладчика это остановка исполнения программы в некоторой точке.
GDB позволяет устанавливать специальные метки в программе -- breakpoint-ы (точки останова),
которая указывает, в каком месте следует остановить выполнение программы. Breakpoint может
быть привязан как к строке в коде, так и к определенному адресу. Во втором случае исполнение
программы будет остановлено перед исполнением инструкции, расположенной по указанному адресу.

После остановки программы, GDB позволяет выполнять множество различных операций,
полезных для поиска ошибок в коде.

Например, GDB позволяет просматривать значение переменных и изменять их. Для низкоуровневой
отладки существует аналогичная возможность отслеживания и редактирования значений определенных
регистров.

Следующей важной возможностью GDB является просмотр информации о текущем стековом фрейме и
стеке вызова функций.

Также, весьма полезной функцией является вызов отдельных функций программы.

\subsection {Отладочная информация: DWARF}
\label{gdb:debuginfo}

Отладочная информация -- данные, которые компилятор вставляет в исполняемые файлы. Эти
данные позволяются GDB понять, какие существуют переменные, функции, их местонахождение,
как соотносятся между собой машинные инструкции и исходный код и т.~д.

DWARF -- это современный формат отладочной информации, который используется в компиляторах GCC
и LLVM и поддерживается GDB.

Стандарт DWARF разработан так, чтобы быть применимым к множеству существующих языков, а также
иметь возможности к расширению для будущих языков.

Запись отладочной информации (Debugging Information Entry, DIE) -- это базовая единица
данных в формате DWARF. Записи отладочной информации хранятся в специальны1х секциях
объектного файла:

\begin{itemize}
\item \texttt{.debug\_info}~--~основная информация о структурах, функциях, переменных и т.~д.
\item \texttt{.debug\_str}~--~хранит строки, используемые в других секциях
\item \texttt{.debug\_line}~--~соответствие между строками исходного кода и адресами
\item \texttt{.debug\_loclists}~--~описывает местоположение переменных в различные моменты
исполнения программы (на регистрах, стеке или в памяти)
\item \texttt{.debug\_rnglist}~--~список диапазонов адресов, используется, когда адреса
для записей отладочной информации не могут быть описаны непрерывным диапазоном
\item \texttt{.debug\_frame}~--~информация для восстановления стека вызовов
\item \texttt{.debug\_macro}~--~описывает препроцессорные директивы (макросы)
\end{itemize}

DWARF использует наборы таких записей, чтобы описать структуру программы. Каждая запись
состоит из тега (tag), определяющего тип описываемой сущности (например функция, переменная
или название типа), и атрибутов, задающих конкретные свойства.

Рассмотрим генерацию DWARF информации на конкретном примере. Здесь и далее для компиляции
я буду использовать LLVM Clang 19.1.0 (если не указано иное) для архитектуры RISC-V,
а для наглядного отображения DWARF информации -- инструмент llvm-dwarfdump.
Данный инструмент сканирует DWARF секции в
объектных файлах и выводит содержимое в удобочитаемом виде.

Итак, возьмем простую функцию с Листинга \ref{lst:simple_example} и посмотрим, какую
DWARF информацию генерирует для нее компилятор.

\end{lstlisting}
\end{samepage}

Для данной функции будет сгенерирована следующая DWARF информация.

На Листинге \ref{lst:simple_example_dwarf} можно увидеть тег \texttt{DW\_TAG\_subprogram},
указывающий на то, что данная запись описывает некоторую функцию. По тегу \texttt{DW\_AT\_name}
мы можем определить, что это функция с именем \texttt{foo}.

Атрибуты \texttt{DW\_AT\_low\_pc} и \texttt{DW\_AT\_high\_pc} описывают диапазон адресов в машинном
коде, в котором располагается данная функция.

Содержимое \texttt{DW\_AT\_frame\_base} описывает значение базового адреса фрейма данной
функции. Для данной функции адрес ее фрейма будет располагаться на регистре \texttt{x8}.

Для описания типа возвращаемого функцией значения, используется атрибут \texttt{DW\_AT\_type}.

\subsection {Необходимая информация о внутреннем устройстве GDB}
\label{gdb:internals}

Рассмотрим поэтапно процесс вызова функции с помощью команды \texttt{call} в GDB.

\label{fig:gdb_pipeline}

После вызова пользователем команды \texttt{call foo(args)}, GDB передает полученное выражение на парсинг.
На этапе парсинга происходит вычисление выражения \texttt{foo(args)}, строится дерево выражения.
Далее, GDB начинает интерпретацию выражения путем обхода дерева. Когда GDB встречает узел, который
соответствует вызову функции, он переходит к подготовке вызова. На этапе подготовки происходит
выделение стекового фрейма, сохранение значений регистров, размещение аргументов функции в регистрах или
памяти, установка PC (program counter) и SP (stack pointer). После этого GDB запускает исполнение
программы до момента возврата из функции.

Далее приведена информация о некоторых функциях и структурах данных
исходного кода GDB. Это позволит продемонстрировать, каким образом была достигнута
поддержка новых возможностей, а также объяснить, в какие части кода производились вмешательства.

\begin{itemize}

\item \texttt{type}~--~структура, описывающая конкретный экземпляр типа.
Некоторые методы данной структуры:

\begin{itemize}
  \item \texttt{code}~--~код данного типа. Например, TYPE\_CODE\_INT, 

    TYPE\_CODE\_ARRAY или TYPE\_CODE\_TYPEDEF.

  \item \texttt{name}~--~имя данного типа.

  \item \texttt{length}~--~размер типа в байтах.

  \item \texttt{target\_type}~--~метод, возвращающий указатель на объект 
    \texttt{struct type}, т.~е. информацию о каком-то другом типе. Интерпретировать
    информацию об этом новом типе данных следует в зависимости от исходного типа.
    Например, если исходный тип это некоторый массив (\texttt{code} возвращает TYPE\_CODE\_ARRAY),
    то \texttt{target\_type}~--~это тип элементов, из которых этот массив состоит.
    В другом случае, если исходный тип является синонимом типа (\texttt{code} возвращает TYPE\_CODE\_TYPEDEF),
    то \texttt{target\_type}~--~это тот тип, синонимом которого он является.

\end{itemize}

\item Структура \texttt{riscv\_arg\_info}~--~хранит информацию об аргументе функции: его значение, тип, 
      расположение (на регистре/нескольких регистрах или в памяти), размер.

\begin{samepage}
\begin{lstlisting}[language=C++, caption=Структура riscv\_arg\_info, label=lst:struct:riscv_arg_info]
struct riscv_arg_info
{
  const gdb_byte *contents;
  int length;
  int align;

  struct type *type;

  struct location
  {
    enum location_type
    {
      in_reg,
      in_several_regs,
      on_stack,
    } loc_type;

    union
    {
      int regno;
      int offset;
    } loc_data;

    int c_length;
    int c_offset;
  } argloc[2];

  bool is_unnamed;
};
\end{lstlisting}
\end{samepage}

\item Структура \texttt{riscv\_call\_info} -- содержит информацию о том, куда можно поместить аргументы функции, 
      отслеживает свободные регистры и области в памяти.

\begin{samepage}
\begin{lstlisting}[language=C++, caption=Структура riscv\_call\_info, label=lst:struct:riscv_call_info]
struct riscv_call_info
{
  riscv_call_info (struct gdbarch *gdbarch)
    : int_regs (RISCV_A0_REGNUM, RISCV_A0_REGNUM + 7),
      float_regs (RISCV_FA0_REGNUM, RISCV_FA0_REGNUM + 7),
      vector_regs (RISCV_V0_REGNUM + 8, RISCV_V0_REGNUM + 23)
  {
    xlen = riscv_abi_xlen (gdbarch);
    flen = riscv_abi_flen (gdbarch);
    vlenb = riscv_abi_vlenb (gdbarch);

    /* Reduce the number of integer argument registers when using the
    embedded abi (i.e. rv32e).  */
    if (riscv_abi_embedded (gdbarch))
      int_regs.last_regnum = RISCV_A0_REGNUM + 5;

    /* Disable use of floating point registers if needed.  */
    if (!riscv_has_fp_abi (gdbarch))
      float_regs.next_regnum = float_regs.last_regnum + 1;

    /* Disable use of vector registers if needed.  */
    if (!riscv_has_vector_regs (gdbarch))
      vector_regs.available_intervals.clear ();
  }

  /* Track the memory areas used for holding in-memory arguments to a
  call.  */
  struct riscv_memory_offsets memory;

  /* Holds information about the next integer register to use for passing
  an argument.  */
  struct riscv_arg_reg int_regs;

  /* Holds information about the next floating point register to use for
  passing an argument.  */
  struct riscv_arg_reg float_regs;

  /* Holds information about the next vector register to use for
  passing an argument.  */
  struct riscv_vector_arg_reg vector_regs;

  /* The XLEN and FLEN are copied in to this structure for convenience, and
  are just the results of calling RISCV_ABI_XLEN and RISCV_ABI_FLEN.  */
  int xlen;
  int flen;
  int vlenb;
};
\end{lstlisting}
\end{samepage}

\end{itemize}
